# 기획부터 GitHub 이슈까지

## 기본 작업 범위

사용자가 이 프로젝트의 기획을 요청하면 **기획 정리 → 사용자 검토 및 확정 → GitHub 이슈 생성 → 이슈 링크 보고**까지 기본 범위에 포함한다. 확정된 기획의 이슈 등록에는 별도 재승인을 요구하지 않는다. 사용자가 초안·논의만 요청하거나 이슈 생성을 제외하면 그 지시를 따른다.

기획 완료는 에이전트가 초안을 작성했다는 뜻이 아니다. 사용자가 최종 기획을 승인했거나, 세부 결정을 위임하며 끝까지 진행하라고 명시한 경우다. 미결정 사항이 핵심 범위를 바꾸면 확정 전에 확인한다.

## 저장 위치

- 기획·디자인 명세·백로그는 GitHub Issues에서만 관리한다. 대규모 기획은 별도 기획 이슈에 두고 작업 이슈에서 참조한다.
- 저장소에 `docs/renewal/`, 기획용 specs/plans, 로컬 티켓 목록 또는 이슈 본문 사본을 생성하지 않는다. 스킬의 기본 저장 경로보다 이 프로젝트의 GitHub 전용 관리 규칙을 우선한다.
- 논의 중 초안은 대화에서 정리한다. 사용자가 GitHub에 초안 보관을 요청하면 초안 상태로 등록한다.
- GitHub 접근이 막히면 본문 초안을 응답으로 제공하고 미등록 상태를 보고한다. 저장소 파일을 대체 저장소로 만들지 않는다.
- 공통 작업 지침·아키텍처·코드 스타일·검증·배포 절차는 저장소 docs에 유지한다.

## 절차

1. 관련 코드와 기존 GitHub 이슈를 확인한다. 이미 있는 정보는 다시 질문하지 않는다.
2. 목적·사용자·포함/제외 범위·주요 흐름·실패 상태·완료 기준을 대화 또는 GitHub 기획 이슈에 정리한다. 제안과 확정 사항을 구분한다.
3. 사용자 검토를 반영해 기획을 확정한다. 구현은 기획 확정만으로 자동 시작하지 않는다.
4. 대상 저장소와 기존 열린/닫힌 이슈를 확인하고, 같은 목적의 이슈가 있으면 중복 생성 대신 갱신한다. 기존 완료 이슈를 임의로 다시 열지 않는다.
5. 독립적으로 구현·검증할 수 있는 크기로 티켓을 나누고 선행 관계를 기록한다. 서로 다른 승인 기준을 가진 작업을 한 티켓에 과도하게 묶지 않는다.
6. GitHub에 실제 이슈를 생성하거나 갱신한다. 최신 범위와 상태의 기준은 GitHub다. 기존 기획에 따른 이슈의 생성·범위 갱신은 이 절차의 작업 범위에 포함된다.
7. 이슈 번호·제목·본문이 등록됐는지 확인하고, GitHub 기획 이슈와 작업 이슈 사이에 실제 링크를 연결한다. 저장소에 별도 목록을 만들지 않는다.
8. 생성/갱신한 링크와 첫 작업을 보고한다. 인증·권한·네트워크로 막혔다면 미등록임을 밝히고 응답으로 본문 초안을 제공한다.

## 이슈 본문

- 목적과 사용자에게 생기는 변화
- 포함 범위와 제외 범위
- 작업 체크리스트
- 검증 가능한 완료 기준
- 선행 이슈의 실제 번호/링크
- 관련 코드 경로와 GitHub 기획 이슈 링크
- 필요한 실패·빈 상태와 검증 방법

이슈 본문만으로 범위와 완료 기준을 이해할 수 있게 핵심 내용을 포함한다. 상세 기획은 GitHub 기획 이슈로 연결하며, 로컬 기획 파일이나 존재하지 않는 파일 링크를 참조하지 않는다.

### 사람이 읽기 쉬운 작성 기준

- 제목은 무엇을 바꾸거나 확인하는지 구체적으로 쓴다. 본문 첫머리에 목적·사용자에게 생기는 변화·현재 상태를 짧게 요약한다.
- 대화에 참여하지 않은 사람도 이해할 수 있도록 쉬운 한국어와 짧은 문장을 쓴다. 전문 용어는 필요한 만큼만 사용하고, 처음 나올 때 의미와 필요한 이유를 설명한다.
- 본문은 핵심 결정, 이번 작업의 포함/제외 범위, 검증 가능한 완료 기준, 선행·후속 이슈 순으로 정리한다. 작은 작업에 불필요한 섹션을 늘리지 않는다.
- 체크리스트에는 이번 이슈에서 실제 완료할 작업만 둔다. 후속 구현이 있어야 가능한 검증은 담당 후속 이슈의 완료 기준에 넣고 링크로 연결한다. 이슈 사이에 선행 조건이 순환하지 않는지 확인한다.
- 긴 SQL·상세 스키마·원문 로그·조사 과정은 본문에 나열하지 않는다. 필요한 근거는 댓글의 접기 영역이나 관련 GitHub 이슈로 연결한다. 범위·중요한 제약·실패 처리·완료 판단에 필요한 정보는 본문에 남긴다. 비밀정보·개인 입력 원문은 어디에도 게시하지 않는다.
- 같은 설명과 체크리스트를 여러 섹션에 반복하지 않는다. 최신 결정은 해당 본문을 직접 고치고, 과거 결정·조사 기록은 현재 기준과 구분해 보존한다. 하단에 정정 사항만 계속 덧붙여 상충하는 내용을 남기지 않는다.
- 확정 사항·제안·미확인 사항, AI 검증·사용자 검토·승인 대기를 구분한다. 사용자에게 필요한 작업은 무엇을 어디에서 해야 하는지 적고, 없으면 없다고 명시한다.
- 등록하거나 갱신하기 전에 본문만 읽고 “왜 필요한가, 이번에 무엇을 하는가, 언제 완료인가, 다음 작업은 무엇인가”에 답할 수 있는지 검토한다. 요약하면서 필수 요구사항이나 미완료 검증을 삭제하거나 완료로 바꾸지 않는다.

## 구현 진행

1. 사용자가 지정한 이슈의 최신 본문, 선행 이슈, 완료 기준을 확인한다.
2. 현재 브랜치, `git status`, 관련 코드와 기존 변경을 확인한다. 사용자 변경과 다른 작업자의 변경을 보존한다.
3. 한 번에 이슈 하나를 구현한다. 관련 없는 리팩터링과 후속 기능을 함께 넣지 않는다.
4. 디자인 검토가 필요한 작업은 해당 디자인 이슈의 승인 상태를 확인한 뒤 제품 UI를 구현한다.
5. 이슈 범위 안에서 구현·검증하고 결과를 보고한다. 다음 이슈는 사용자가 지정하거나 연속 진행을 명시적으로 맡긴 경우 진행한다.
6. GitHub 이슈 수정·댓글·종료, 커밋·푸시·PR 생성은 사용자가 맡긴 범위에서 수행한다. 로컬 완료를 GitHub 종료로 자동 간주하지 않는다.
7. 피처 개발은 구현 전에 별도 `codex/<issue-number>-<short-name>` 브랜치를 생성하거나 해당 작업의 기존 브랜치를 재사용한다. 기본 브랜치에서 직접 개발하지 않는다. 다른 작업의 브랜치를 재설정하거나 사용자 작업을 이동하지 않는다.
8. 서브에이전트는 사용자 또는 적용 가능한 지침이 위임을 요청할 때만 사용한다.

현재 범위·순서·디자인 승인 상태는 GitHub 기획 및 작업 이슈에서 확인한다.

## 피처 개발 → 최종 검토 → PR → 코드리뷰

1. 작업 시작 전 현재 변경과 브랜치를 확인하고 대상 기본 브랜치를 실제 저장소에서 확인한다. 무조건 `main`이라고 가정하지 않는다. 기존 변경을 보존하며 해당 피처 전용 브랜치에서 작업한다.
2. 구현과 필요한 검증은 로컬에서 완료한다. 완료한 작업은 의미 있는 단위별로 검증 후 반드시 로컬 커밋한다. 관련 없는 변경을 함께 커밋하지 않는다.
3. 개발 중 또는 개발 완료 보고 시점에는 **push하지 않고 PR도 생성하지 않는다.** 백업 목적의 push, 원격 브랜치 생성, 원격에서 직접 코드 파일 수정도 이 제한을 우회하는 방법으로 사용하지 않는다.
4. 사용자에게 변경 요약·로컬 검토 방법·검증 결과·남은 제약을 제공하고 최종 검토를 기다린다. 사용자 수정 요청은 같은 브랜치에 반영하고 다시 검증한다.
5. 사용자가 해당 변경의 **최종 검토 완료와 진행 의사**를 명시하면 push → PR 생성 → 코드리뷰를 추가 재승인 없이 수행한다. ‘계속 개발해’, 중간 디자인 승인, 단순 상태 질문은 최종 승인으로 해석하지 않는다. 경과 시간이나 무응답도 승인이 아니다.
6. 승인 후 브랜치와 diff·검증 결과를 확인하고 작업별 커밋이 준비됐는지 확인한 뒤 일반 push를 수행한다. 강제 push하지 않는다. 기존 원격 PR이 있으면 중복 생성 대신 갱신한다.
7. PR에는 연결 이슈, 실제 최종 변경, 검증 결과와 제한을 적고 사용자에게 링크를 제공한다. 사용 가능한 앱의 PR 첨부 기능이 있으면 생성한 PR을 현재 작업에 첨부한다.
8. PR의 실제 diff를 기준으로 코드리뷰를 수행한다. 정확성·회귀·데이터 보존·오류 처리·접근성을 확인하고, 발견한 문제와 검증 한계를 근거와 함께 보고한다. 리뷰 도구가 없으면 직접 검토하고 사용한 방식을 밝힌다.
9. 리뷰에서 발견한 범위 내 문제는 수정하고 필요한 검증 후 동일 PR에 반영하며 다시 검토한다. 승인된 범위를 바꾸는 기능이나 중요한 제품 결정은 먼저 사용자에게 확인한다.
10. PR 생성이나 코드리뷰 완료를 병합·배포 승인으로 간주하지 않는다. 병합·운영 배포·이슈 종료는 별도 요청 범위에 따른다.

승인 후 동일 PR의 리뷰 수정·재검증·일반 push는 위임된 작업에 포함한다. 새로운 피처의 push에는 새 최종 검토가 필요하다. Git hook이나 검증 명령이 외부 배포를 실행한다면 먼저 그 동작을 확인한다.

## AI 검증과 사용자 검토 구분

개발 완료 보고와 PR 본문에는 다음 세 항목을 구분해 표시한다. 해당 사항이 없으면 ‘없음’으로 명시한다.

- **AI 검증 완료**: 테스트·타입 검사·빌드·코드리뷰·요구사항 충족·반응형·키보드 동작 중 실제 확인한 항목과 결과를 적는다. 자동 검사, 코드 검토, 실제 브라우저 확인을 구분하고, 미실행·실패·접근 제한과 기존 경고를 숨기지 않는다.
- **사용자 검토 필요**: 디자인 취향, 문구의 자연스러움, 사용 흐름 등 최종 제품 판단이 필요한 부분과 AI가 접근할 수 없는 계정·운영 환경 확인을 구체적인 미완료 체크리스트로 적는다. 검토할 화면·링크, 확인할 동작과 판단 기준을 제공한다. AI가 확인 가능한 기술 검증은 먼저 수행하고 사용자에게 반복 검증을 떠넘기지 않는다. 사용자 확인 전에는 체크를 완료하지 않는다.
- **승인 대기 작업**: push·PR 생성·병합·운영 배포 등 다음 작업의 현재 상태와 필요한 승인만 별도로 적는다. 이미 받은 승인을 다시 요구하거나 사용자 검토 항목의 완료를 다른 작업에 대한 포괄 승인으로 해석하지 않는다. 승인 기준은 위의 피처 개발 절차를 따른다.

PR 생성 시 사용자가 이미 확인한 검토 항목은 확인된 내용과 근거를 기록하고, 남은 사용자 검토 항목만 미완료로 표시한다. AI 검증 완료를 사용자 최종 검토 완료나 병합·배포 승인으로 표현하지 않는다.

## 작업별 로컬 커밋

- 하나의 목적과 검증 결과를 가진 작업 단위마다 커밋한다. 작은 티켓은 한 커밋, 여러 독립 작업을 포함한 티켓은 작업별 여러 커밋으로 나눈다.
- 파일 저장마다 커밋하거나, 서로 다른 작업을 마지막에 하나의 커밋으로 합치지 않는다.
- 변경 파일과 staged diff를 확인하고 현재 작업 파일 또는 hunk만 선별한다. 사용자나 다른 작업자의 변경을 섞지 않는다.
- 해당 변경에 필요한 검증을 먼저 수행한다. 문서 변경은 경로·내용·포맷 확인으로 충분하다. 미완료 또는 실패한 검증을 통과한 것으로 기록하지 않는다.
- 커밋 제목과 본문의 변경 설명은 한글로 작성한다. `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:` 접두사와 코드 식별자·파일명은 원문을 유지할 수 있다. 관련 이슈가 있으면 번호를 포함한다.
- 예: `feat: 지난 당첨번호 카드 추가 (#4)`, `docs: 커밋 메시지 한글 작성 규칙 추가`.
- 검토 수정은 추가 커밋으로 남긴다. 사용자 요청 없이 기존 커밋을 amend하거나 squash/rebase로 재작성하지 않는다.
- 완료 보고에 커밋 해시·작업 요약·검증 결과를 포함한다. 커밋은 push 권한을 의미하지 않는다.

## Git과 외부 작업

- 기획 및 이슈 등록의 기본 권한에는 구현·커밋·푸시·PR·병합·배포·기존 이슈 종료가 포함되지 않는다. 해당 작업은 사용자가 맡긴 범위에 따라 수행한다.
- 피처 전용 브랜치는 `codex/` 접두사를 사용한다. 구현 완료와 최종 검토 승인 전에는 push하지 않는다.
- GitHub 접근은 사용 가능한 커넥터, 인증된 CLI 또는 브라우저로 수행한다. 인증 정보 추출로 우회하지 않는다.
- 신규 이슈에 담당자·마감일·프로젝트·마일스톤을 임의 배정하지 않는다. 필요한 기존 분류만 사용한다.
